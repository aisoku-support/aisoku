# 20261005-033 Clef-flash 分類・除外判定の評価

## 結論

**採用判断: D（現時点では採用しない）**

Clef-flashのchoice出力は固定カテゴリ選択や二値の除外判定に技術的には適合する。しかし、現行分類との同一データ比較、正解ラベルに対する精度、反復時の安定性、実測レイテンシがなく、採用候補と判断する根拠がまだない。さらに現行Stage 1はカテゴリに加えて`subject`と`event`を抽出するため、Clef-flash単独では置き換えにならない。今回はモデルAPIを呼ばず、本番処理・環境も変更していない。

## 現行方式

- `topic-processing` のStage 1はGroq Chat Completionsを使い、JST時間帯に応じQwen 3.8 27B / GPT-OSS 20Bを主モデル・fallbackとして切り替える。主モデルのtimeout時のみ同一記事を最大1回再試行し、失敗時はfallbackへ進む。
- 1 requestで`subject`（40文字以内）、`event`（50文字以内）、`category`を生成する。カテゴリは`トレンド`、`エンタメ`、`サブカル`、`マネー`、`IT・ガジェット`、`除外`の6値。temperatureは0、strict JSON Schemaを利用する。
- parserは出力形式、記事との対応、カテゴリ、文字数等を検証する。`除外`はStage 1で処理を終え、facts生成・Embedding・Topic作成へ進めない。Stage 1前の機械フィルタ除外とは区別する。
- 根拠: `docs/CURRENT_SPEC.md` 8.6.3–8.6.4、`supabase/functions/_shared/topic/stage1.ts`、`gemma_parser.ts`、`topic-processing/index.ts`。

## Clef-flashで確認できた仕様

確認日: 2026-10-05。Cloudflare Workers AI公式モデル資料・価格資料を確認。

- モデルIDは`@cf/cloudflare/clef-flash`。9Bのマルチモーダル判断モデルで、text/JSON/image/videoのstateと型付き質問を入力し、許可された各回答の確率を返す。コンテキスト上限は65,536 tokens。
- 質問は`noul`（真偽判断）、`choice`（名前付き選択肢とcriteria）、`score`（尺度）の型。1リクエストあたり1〜64問。`state`は文字列または構造化データ。長いstateは上限に合わせ切り詰められる。
- 応答例には`model`、質問IDごとの`answers`、`usage`がある。choiceは選択肢ごとの確率を返すため、カテゴリ候補を機械可読なキーへ対応づけられる。自由文パースを避けられる点は現行JSON生成と異なる。
- 価格表記は入力100万tokensあたり$0.09（=1,000 input tokensあたり$0.00009）。Cloudflare共通枠としてWorkers AIは1日10,000 Neurons無料、超過分は$0.011/1,000 Neurons。価格資料にはモデル別の入力単価があり、Clef-flashの出力単価は確認できなかった。今回の入力token量が実測されていないため、記事単位の費用は算出していない。
- 出典: [Clef-flash model docs](https://developers.cloudflare.com/workers-ai/models/clef-flash/)、[Workers AI pricing](https://developers.cloudflare.com/workers-ai/platform/pricing/)、[Clef launch](https://developers.cloudflare.com/changelog/post/2026-10-01-clef-workers-ai/)。

## 評価方法と結果

- 実装・仕様・既存分類テストを静的に確認した。既存のローカルベンチマーク素材は記事生成・facts・コメントやTopic clustering等が中心で、この依頼に必要な同一記事のStage 1正解カテゴリ・除外ラベル付き比較セットは確認できなかった。新しいデータ作成や外部API呼び出しは行っていない。
- **カテゴリ適合性:** choiceで6値を選ぶ形式は適合する。入力が記事の長文本文を含む場合、state切り詰めの有無を監視し入力を揃える必要がある。`subject/event`生成は対象外なので、置換には別処理が要る。
- **除外適合性:** `noul`または「5カテゴリ＋除外」のchoiceで表現可能。ただし除外は掲載・Topic作成を止める終端判断なので、誤除外率と確率閾値を正解ラベル付きで検証しないまま本番ゲートに使うのは不適切。
- **精度・安定性:** 現行方式との同一入力比較なし。Clef-flashの確率出力は選択肢の相対確率であり、正解確率として校正済みであることや、同一入力の反復安定性は公式仕様で確認できなかった。数値は未確認。
- **速度・token:** Clef-flashの「fast」という説明と65,536 token上限は確認できたが、p50/p95 latency・処理速度保証は未確認。実入力tokens、応答usageの内訳と既存Groqの同条件token量が揃わず、比較値は未確認。
- **接続安全性:** choiceの回答キーを既存6カテゴリのallowlistへ写像し、欠落・未知キー・曖昧な確率は失敗扱いにする接続は設計可能。probabilityの採用閾値、低確信時のfallback、`subject/event`をどのモデルに残すかは実験と仕様判断が必要。構造化出力は安全性を高めうるが、誤判定自体は防がない。
- **アーキテクチャ配置案（将来検証時）:** 既存の機械フィルタ後、Stage 1位置でShadow比較するのが適切。正解ラベル付きオフライン比較を通過した後も、当初は既存Groqの判定と並行記録し、除外の誤りを確認する。`subject/event`生成と既存parserの契約を保てる形が定まるまでは切替しない。Cloudflare呼び出しは既存Edge worker境界とquota/observability設計を確認してから別途設計する。
